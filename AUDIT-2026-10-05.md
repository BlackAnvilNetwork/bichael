# Bellgrave self-audit, 2026-10-05

Branch `audit/self-audit-2026-10-05`, based on `main` @ `ad67d07`. Scope: Rust engine and wasm API, Foundry contracts and deploy scripts, TS server, web client, tooling.

Ground rules for this branch:
- No engine source changes. `LOCAL_RULESET_HASH` and the wasm sha256 pin are unchanged.
- No contract changes. No change to the meaning, serialization, or hash of any existing log event.
- Every new replay check was run against a copy of the live data dir: 175-entry legacy snapshot plus a 5-line journal, seq 176..180. It opens at `length 180`. All 11 bind rows were kept, and no torn-tail or dropped-row backup was written.

Status key:
- **FIXED**: fixed in this branch, with tests.
- **PARTIAL**: risk reduced in this branch; the rest needs a decision.
- **DECISION**: needs the owner to pick an approach.
- **REDEPLOY**: needs a contract or ruleset change and an anvil redeploy.
- **TRACKED #N**: already on file. Noted only, and only if it is worse than described.

## High

### H1. Nothing stops two processes from writing the same data dir: FIXED
- **Where:** `apps/server/src/lok-world.ts:183` (constructor). New file: `apps/server/src/data-dir-lock.ts`.
- **Impact:** A second process that opens `apps/server/data` keeps its own in-memory engine. Examples: `pnpm dev:server` / `tsx watch` started next to `start`, a scheduled run, or a maintenance script. Both processes append to `lok-world.jsonl` and rewrite `lok-world.json` and `lok-bind.json`. The on-disk hash chain forks. The next restart then either refuses the journal (`lok journal refused` / `corrupt`) or silently keeps one side. This is the failure class behind today's recovery.
- **Fix:**
  - The `LokWorld` constructor takes an O_EXCL lock file `lok-world.lock` holding `{pid, host, startedAt}` before it reads or writes anything.
  - A lock held by another live pid on this host, or by another host, makes the open throw. The boot path already turns that into `process.exit(1)` with nothing written.
  - A stale lock (dead pid) is taken over. The same pid may reopen (tests do).
  - The lock is removed on exit. `LOK_ALLOW_SHARED_DATA_DIR=1` is the operator override.
- **Tests:** `audit-2026-10-05.test.ts`: "a second live process cannot open…", "a stale lock…", "a lock held on another host…".
- **Caveat:** This only protects once the running server has been restarted on this code. The server running now (pid 17980) predates it and does not write the lock. On Windows a recycled pid can make a crashed server's lock look alive. The error then names the file and the override.

### H2. A torn final journal line corrupts the journal on the next append: FIXED
- **Where:** `apps/server/src/lok-world.ts:892` `replayJournal`, `:935` `repairJournalTail`.
- **Before:**
  - On a crash mid-`appendFileSync`, the old replay skipped an unparseable last line but set `journalBytes = raw.length`.
  - The next event was appended directly onto the fragment, so `<fragment>{"seq":…}\n` became one line.
  - The next restart threw `lok journal is corrupt` and refused to start. Recovering meant hand-editing the journal, and the first event after the crash was lost.
- **Fix:**
  - An unparseable fragment after the last newline is copied to `lok-world.jsonl.torn-<stamp>` and truncated away. It never reached the engine.
  - A complete final record that only lacks its `\n` is kept and terminated.
  - Any other unparseable line still throws.
- **Tests:** "a torn final journal line is cut off…", "a complete final journal record without its newline…".

### H3. Replay takes each event's touch set from the document: a hash-valid document can mint: DECISION / REDEPLOY (related #177)
- **Where:**
  - `contracts/lok-log/engine/src/world.rs:750-766` (`World::load`). `touch` is the set of characters whose chains carry the entry.
  - `effects()` at `:1090` gates every credit and debit on `touch`.
  - `affected()` (`:784`) is only called on the append path (`:482`), never on replay.
- **Impact:**
  - Entry hashes are unkeyed (`entry_hash(prev, index, input)`), so anyone can recompute them.
  - A document can put a `SendKek` / `SendItem` / `SendInbox` entry only on the receiver's chain. Replay credits the receiver and never debits the sender, which is a mint that verifies.
  - Checks that live only in `affected()` are also skipped on replay, for example `Ask` with `item_id == 0` / `listing_id == 0`.
  - The live server is not exploitable through this, because it only replays its own file. Any third party that verifies a published document, and any future checkpoint verifier, is.
- **Recommendation:**
  - In `load()`, compute `affected(&input)` against the pre-event world and require it to equal `touch`.
  - First prove on the committed logs, with a test over the live and regression fixtures, that every historical group already satisfies this. Adding a replay check must not change what already-written logs mean (#206 lesson).
  - This changes the wasm, so the pin and `LOCAL_RULESET_HASH` change and anvil needs the new ruleset accepted.

### H4. A withdrawal debit can be stranded, and then every later withdrawal fails: PARTIAL
- **Where:**
  - `apps/server/src/index.ts:1046` `queuePlayerWithdrawal`.
  - `apps/server/src/lok-vault.ts` `queueKekWithdrawalNow`, which has the new `debit` hook.
  - `contracts/lok-log/engine/src/world.rs:1464` `undo_last_withdraw`.
- **Before:**
  - The `WithdrawKek` debit was appended before about 8 `cast` calls: chain-id, owner, stateRoot, logIndex, version, ownerOf, isAccepted, signer.
  - On any definite refusal (most commonly "local ruleset is not accepted yet"), the server called `undoWithdraw`. That only pops the *last* entry of that character.
  - Several things can append to the character during that window without its KEK lock: a level-up, loot drop, craft skill, an incoming `sendKek`, or a sale of its ask. If any of them did, the undo failed, the KEK stayed debited, and the in-memory reserve vanished on restart.
  - After that the checkpoint drafted for the next withdrawal carries the extra `kekOut`. `checkpointFor().kekOut !== amount` refuses it, so the character can never withdraw again.
- **Fixed here:**
  - The debit now runs inside the vault call, after chain-id and the ruleset check and immediately before `prepare`.
  - Refusals before that point append nothing. An undo is only attempted when this attempt actually appended (`debited` flag).
  - Tests: "an unaccepted ruleset refuses … before the log debit", "the withdrawal debit runs after the ruleset check…".
- **Also fixed:** the `confirm() === false` branch in `kek-guard.ts:258` told the player "Reserved KEK was returned" while the log debit stayed. The message now says the debit was kept. The debit is deliberately *not* undone there, because a dropped receipt is not a revert: if the tx lands later, an undo would let the KEK be paid out and stay spendable. Test: "a withdrawal the vault does not show does not claim the KEK was returned".
- **Remaining (DECISION):**
  - The window from debit to a definite refusal still spans ownerOf/transfer, signing, and the send.
  - The durable fix is a compensating `WithdrawCancelled` event instead of popping, or holding all appends for that token during the attempt. A new event is an engine and ruleset change. The `WithdrawKek` + vault-cancel leftover in #205 has the same root cause.

### H5. One bad chain event halts the deposit watcher for every player: DECISION
- **Where:** `apps/server/src/lok-chain.ts:216-232` (the cursor stops at the failing block) and `:297` (logs "halted").
- **Impact:**
  - Any inbound the engine refuses for a reason other than "already applied" pins the cursor at that block forever. Examples: a `depositKek` / `ItemImportRequested` for a token that has no log character, or an amount or itemId the engine rejects.
  - `CharacterCheckpoint.depositKek` is callable by any NFT owner, and NFTs can be minted straight from the factory without the server.
  - So anyone on the chain can stop deposits for everyone. Factory mints outside the server also break the next-id assumption in `linkCharacterNft`.
- **Recommendation:**
  - Classify refusals. Permanently unprocessable events (unknown token, invalid id) go to a persisted quarantine list with an operator alert, and the cursor moves past them.
  - Only nonce gaps (the #206 "halt on nonce gaps" rule) and transient errors should halt.
  - This is a policy decision because a quarantined deposit is KEK in custody with no log credit.

## Medium

### M1. Journal `seq` was never checked on replay: FIXED
- **Where:** `lok-world.ts:892`. Each journal line already records the log length after it was applied (`{"seq": length, cmd}`), but replay ignored it.
- **Impact:** A duplicated line (copy/paste recovery, an append retried by a tool) or a snapshot paired with the wrong journal was re-applied silently whenever the engine accepted it. A second `sendKek` is accepted.
- **Fix:** After applying each line, replay requires `rec.seq === this.length` and throws a clear mismatch error otherwise. Validated against the live copy: seq 176..180 all match.
- **Test:** "a duplicated journal line is refused instead of applied twice".

### M2. Startup reconcile silently deletes `lok-bind.json` rows: FIXED
- **Where:** `lok-world.ts:1014` `reconcileBind`.
- **Impact:** Rows whose token is not in the log are dropped and the file is rewritten at startup. After a recovery to an older or empty log, every newer character's wallet binding and name were gone for good. The bind file is the only record of them.
- **Fix:** Dropped rows are written to `lok-bind.dropped-<stamp>.json` with the log length, and an error is logged, before the rewrite. The behavior is otherwise unchanged.
- **Test:** "bind rows dropped by reconcile are backed up…".

### M3. A corrupt `lok-vault-pending.json` was silently reset and then overwritten: FIXED
- **Where:** `apps/server/src/lok-vault.ts` `loadVaultPending`.
- **Impact:** A parse error became `[]`, and the next enqueue overwrote the file, losing queued `sinkKek` / `reassignKek` ops. On-chain vault claims then drift from the log with no record.
- **Fix:** It throws now, the same way `loadQueues` and `readWithdrawIntents` already do. Boot exits with the file untouched.
- **Test:** "a corrupt lok-vault-pending.json refuses to load…".

### M4. An unhandled rejection in the `auth` handler crashes the whole server: FIXED
- **Where:** `apps/server/src/index.ts`, the `msg.type === "auth"` branch (`verifyAuthLogin(...).then(...)` had no `.catch`).
- **Impact:** After a valid signature, `adoptOrphanLogs` → `createPlayer` → `readPlayerProgress` throws on a corrupt or partial save. That was an unhandled rejection, which kills Node 22 and drops every connected player. The same wallet logging in again crash-loops the server.
- **Fix:** Added a `.catch` that logs and sends an error. Also added a `.catch` on the `linkCharacterNft(...).then` in `char/create`. No unit test: `index.ts` starts the server on import.

### M5. Boot reconcile drops withdrawal intents without undoing the debit: DECISION
- **Where:** `apps/server/src/kek-guard.ts:159` (`id == null` → dropped), `:170` (not on chain → dropped). `index.ts:464` `reconcileQueuedWithdrawals`.
- **Impact:**
  - The debit is appended before the queue. The doc comment on `guardedWithdraw` says the opposite, because `index.ts` passes `debit: () => ok`.
  - A crash between the debit and the send therefore leaves a debited log with no withdrawal on chain, and the intent is discarded at boot. The KEK is stranded, and H4's `kekOut` mismatch then blocks that character.
  - A boot-time `undoWithdraw` is not safe either. See L9: the server's engine always reports `committed = 0`.
- **Recommendation:** At boot, compare the character's on-chain `logIndex` / `stateRoot` with the log. A `WithdrawKek` past the committed index with no matching vault row should be compensated with a cancel event (the same event H4 needs).

### M6. Vault sync retries are not idempotent: REDEPLOY
- **Where:** `lok-vault.ts:528` `runOneVaultOp`, `:360` `reassignKekOnchain`, `:386` `sinkKekOnchain`.
- **Impact:** A `reassignKek` / `sinkKek` broadcast that times out after it was mined is retried, up to 12 attempts before it is stranded. On-chain claims then move twice.
- **Fix options:** Add an op id to `reassignKek` / `sinkKek` with a used-id map in `CharacterCheckpoint` (redeploy). Or, before a retry, check the receipt or the claim delta.

### M7. `ExportItem` means two different things: latent item dupe: TRACKED #203/#205 (worse than described)
- **Where:**
  - `world.rs:515-542` (`checkpoint_covering` turns every `ExportItem` into an on-chain ERC-1155 export).
  - `index.ts:720` `handleLokExport` ("Export to bag") and the startup bag reconcile both log `ExportItem`.
  - `lok-vault.ts:657` `tupleOf` hard-codes `exports=[]`.
- **Impact:** This is latent today only because of the `exports=[]` hard-code. Once item exports are wired, every in-game move from log to bag would also mint on chain, which is a dupe, not just a mismatch. A distinct `BagExport` event is needed before ERC-1155 goes live.

### M8. Buys and bids skipped the vault-sync gate: FIXED
- **Where:** `index.ts:1018` `handleLokBuy`, `:1095` `handleLokBid`.
- **Impact:** `sendKek`, spend, and respec all refuse while a vault op is stranded or the checkpoint is paused. Buys did not, yet they move vault claims and enqueue `reassignKek`, which keeps adding work to a sync that is already stuck.
- **Fix:** Buys and bids now wait on the same `vaultClaimBlocked()` gate. Buy semantics (lowest ask, the 32-fill cap) are unchanged.

### M9. `scripts/bind-unowned-wallets.ts` races the running server: PARTIAL
- **Impact:** The script rewrites `lok-bind.json` while the server holds its own copy in memory. Whichever writes last wins. The script also binds `replayed:<token>` placeholder rows.
- **Fix:** The script refuses while a live process holds the data-dir lock (H1).
- **DECISION:** Should placeholder rows be skipped unless a flag is passed? That is left as is, because it may be the intended recovery tool.

### M10. Owner-key sends are not serialized across code paths: DECISION
- **Where:** `lok-vault.ts:138-139` (deposit), `:302` (NFT transfer), `:327` (factory mint), `:375` / `:397` (reassign/sink, under `withKeyQueue`), `:785` / `:859` (withdrawal, under `withVaultQueue`), `:904` (claim).
- **Impact:** Two concurrent `cast send` calls with `LOK_OWNER_KEY` can pick the same nonce ("nonce too low" or a replaced tx). On automining anvil this is rare. On a real chain it is a lost or reordered op.
- **Fix:** Route every owner-key send through a single `withKeyQueue(ownerAddress)` helper. Do not nest it inside the existing queues, or they deadlock. Not done here, to keep the vault path's behavior identical for review.

### M11. Persistence durability on Windows/OneDrive: DECISION
- **Where:** every `atomicWrite` / `writeTextAtomic` (write tmp, then `renameSync`). No fsync, and the journal append has no fsync.
- **Impact:**
  - On power loss, rename-before-data can leave a zero-length snapshot or bind file.
  - The data dir lives under OneDrive. Sync can hold files open, so `renameSync` fails with EPERM/EBUSY and that write throws mid-action.
- **Recommendation:** Move the data dir out of OneDrive (`LOK_DATA_DIR`). Add `fsyncSync` on tmp files and the journal fd, and a short EPERM retry on rename.

## Low

- **L1. The quantity-buy UI ignored the 32-fill cap. FIXED.**
  - Where: `packages/protocol/src/auction-book.ts`.
  - Before: the UI quoted a total that one click would not buy.
  - Fix: `planQuantityFills` takes `maxFills` (default `MAX_QUANTITY_FILLS = 32`) and returns `capped`. `auction-house.tsx` says the click stops at 32 asks.
  - Test: the protocol constant equals the server's `MAX_FILLS_PER_BUY_MESSAGE`.
- **L2. Discarding base mats did nothing. FIXED.**
  - Where: `index.ts:2835` `handleDiscard`.
  - Before: the discard removed the bag row, but `baseMats` kept the count. `syncBaseMatsToInventory` (run on every snapshot) put the stack straight back, and it stayed craftable.
  - Fix: discard now syncs `baseMats` for non-starter base items. No base-kind item has a `consume` effect (checked against the catalog), so this was not a consumable dupe.
  - Not unit-tested, because `index.ts` cannot be imported in tests.
- **L3. Corrupt deposit cursor.** `readDepositCursor` (`lok-chain.ts:132`) silently restarts from block 0 on a corrupt cursor file. Replays are deduped by nonce, so this is only slow. It should throw like the other state files.
- **L4. No crash policy.** There is no `process.on('uncaughtException' | 'unhandledRejection')` policy. A synchronous throw in a message handler kills the process. That is fail-stop and arguably correct for persistence errors, but the policy should be chosen on purpose.
- **L5. Old socket stays logged in.** After the same wallet signs in on a new socket, the old socket stays authenticated. Same owner, so low.
- **L6. Legacy settle.** `lok/settle` (`index.ts:4783`) can be triggered by anyone on legacy (non-book) listings, which have no end time. Legacy listings only.
- **L7. Doc and text drift.**
  - Fixed here: the protocol comments for `lok/import` ("Refused by the server") and `lok/withdrawKek` ("Does not debit").
  - Still open:
    - The `guardedWithdraw` doc says "debit after queue".
    - Mangled escapes in `event.rs`/`world.rs` doc comments (`\min_price\`, `\mount\`, `ow\`).
    - Indentation glitches at `event.rs:276` and `chain.rs:615`.
    - A user-visible mojibake string "You fallâ€¦" at `index.ts:2868`.
- **L8. Dead code.** `debitAfterQueue` (`lok-vault.ts:143`) is unused and describes the opposite ordering from the live flow. Delete it, or wire it in, to prevent drift.
- **L9. `committed` is always 0 in the server engine.**
  - `commit_span` is not reachable through the wasm gate, so `undo_last_withdraw` (`world.rs:1464-1471`) cannot tell an entry the chain has committed from one it has not.
  - Harmless while undo only follows a refused send. It would be unsafe for any boot-time undo (see M5).
- **L10. The lock is advisory.** It does not stop a process that skips `LokWorld`. Examples: the bind script, which is now guarded, or a manual copy over the data dir.
